Gotchas encountered and fixed during submission:

  environment...") had defaulted to "No" from a carried-over prior answer despite being a strong,
  confirmed match — corrected to "Yes." Indeed's "answered based on your previous responses"
  carryover feature can silently import wrong answers; verify every pre-filled screener answer
  individually, don't trust the default.
- Voluntary self-identification radios (Disability status, Veteran status) appeared to be set via
  `form_input` with value "true" but the UI never actually reflected the selection (silent no-op on
  these particular custom radio components) — caught by screenshot-verifying after the fact, fixed
  via direct coordinate clicks instead. Race/Ethnicity and Gender fields (a custom combobox and a
  radio group respectively) worked fine via direct click. Lesson: for this ATS's self-ID radios,
  don't trust form_input's return value as confirmation — always screenshot-verify the actual
  selected state.
- On the final Review page, an optional "Add supporting documents" -> "Write a cover letter" text
  box was PRE-FILLED with a completely unrelated, stale cover letter (mentioning "flexEngage" and
  "Cysiv" in a different context) carried over from some earlier, unrelated application in Kyle's
  Indeed history — same bug class as the resume-carryover and screener-answer-carryover issues above.
  A plain click + ctrl+a + type did NOT clear the old text; it merely prepended the new text before
  the stale text. Fix: used `javascript_tool` to grab the native HTMLTextAreaElement value setter,
  call it directly with the correct full cover-letter text, then dispatch `input` and `change` events
  manually. This is the same reliable pattern as the Ashby email-retype-and-blur fix — always assume
  Indeed's answer/text carryover features can inject wrong content, and always screenshot-verify
  after any fix on a pre-filled field, since even ctrl+a/select-all can fail silently on these custom
  form widgets.
